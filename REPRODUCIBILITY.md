# Reproducibility Audit

**Audited:** 2026-08-14, against the 2026-08 redesign
working tree.

This document answers one question for every visible component of
`https://miccai-explorer.github.io/`:

> Could someone who has only this repository; no LLM, no chat transcript, no memory of
> how it was built; regenerate this component?

Every row names the exact function(s) that produce it, so the answer can be checked
rather than taken on trust.

---

## Headline result

**Re-verified 2026-08-22**, after the Orals pages, the All Papers page, and the
review-parser fixes. The numbers below are from that pass, not the original one.

**Every visual on the site is generated by committed code. Nothing was written in a
scratchpad and lost.** All 60 chart files, all four page templates, all tables and all
stat strips trace to a named function in `analysis/build_charts.py`,
`analysis/build_oral_charts.py`, or `analysis/build_site.py`. A verification pass over
the 68 generated pages (8 pages plus 60 chart files) resolved all 204 internal
`src`/`href` references against files on disk: zero missing, zero orphaned.

The gaps are not in the plotting code. They are in **six hand-made inputs that feed the
plotting code**; cluster names, submission counts, logo colours, logo images, host
cities, and the white-background flag. All six are committed as data, so the site
rebuilds today. None of them can be *re-derived* by running code, which matters the
moment you add a year or re-run the clustering.

---

## Three levels of reproducibility

The answer differs depending on what you are trying to redo. Each table below reports
against all three.

| Level | What it means | Command(s) | Verdict |
|---|---|---|---|
| **L1; Rebuild the site** | Fresh clone → identical website, using the committed data | `python analysis/build_charts.py && python analysis/build_site.py` | **Fully reproducible.** This is what CI does. |
| **L2; Regenerate the data** | Re-scrape the web, re-embed, re-cluster, then rebuild | `scrape.py` → `normalize.py` → `embed.py` → `use_model.py` → L1 | **Partial.** Code exists for every step, but the 20 cluster names come out as `"Cluster 0" … "Cluster 19"` placeholders. |
| **L3; Add a new year (2026)** | Extend the site to a year that does not exist yet | config block + L2 + L1 | **Partial.** Five manual inputs are needed and only one of them (the config block) has code that reads it from a file. |

## 5. Gaps: inputs with no generating code

These are the only reproducibility gaps on the site. Each is committed as data, so **L1
is unaffected**; each blocks L2 or L3.

### G1: Cluster names · **closed 2026-09-08** · was highest impact

`data/processed/cluster_labels_{model}.json` holds the 20 human-readable topic names.
They appear in the legend and hover of the semantic map on **every page**, and are
counted by the "Research Clusters" stat card.

This gap said the names "stay valid as long as the model, projection, paper set and seed
are unchanged, but that is a property of the seed, not something the repo enforces or
checks." That turned out to be not a risk but a live defect: the specter2 clustering had
been recomputed at some point after its names were written, and because KMeans hands the
same groups out in a different order between runs, **all twenty names were on the wrong
clusters on the published site.** Nothing failed, because the file made no claim about
which partition it described.

Closed in two halves:

- **Deriving the names is now mechanical.** `analysis/describe_clusters.py` prints, per
  cluster, the top TF-IDF terms and the 12 titles nearest the centroid. Re-running
  `embed.py` no longer loses the ability to recover names, so L2 is no longer blocked.
- **The names now say what they describe.** `analysis/cluster_labels.py` stores a
  SHA-256 fingerprint of the `paper_id -> cluster_id` assignment alongside them, and
  `embed.py`, `use_model.py` and `build_charts.py` each verify it and raise on a
  mismatch. `tests/test_cluster_labels.py` re-breaks the bug three ways.

Naming still requires a human, and no fingerprint can tell a good name from a bad one.
What is enforced is that the names belong to the clustering being drawn.

### G2: Submission counts · blocks L3

`num_papers_submitted.yaml` holds five hand-typed integers. They drive three of the nine
overview panels (Submissions, Acceptance Rate, Early Accepted) and the rebuttal Sankey
caption via `pct_early_subs`. The header comment says "Sourced from official MICCAI
conference reports" but records no URL, report title or date per year, so the figures
cannot be independently checked or extended without knowing where to look.

**To close:** add a source URL and access date as a comment beside each year.

### G3: Year colours, stored three times · blocks L3

`logo_colors.yaml` is read by **no code and written by no code**; both Python files only
mention it in a comment. The values were eyedropped from the logo images by hand and then
copied into three separate Python dicts:

| Copy | Location | Used for |
|---|---|---|
| `YEAR_COLORS` | `build_charts.py:119` | bar colour per year on the overview grid |
| `YEAR_PALETTES` | `build_charts.py:129` | main/secondary colour on year-page charts |
| `YEAR_META_RAW` | `build_site.py:41` | CSS accent theme on year pages |

Nothing keeps the three in sync, and the selection rule is undocumented: 2025 uses
`#692f90` (the *third* logo primary) in `YEAR_COLORS` but `#2b50a3` (the *second*) in
`YEAR_PALETTES`. That is a deliberate legibility choice, but a reproducer has no way to
know which primary to pick for a new year.

**To close:** have both scripts read `logo_colors.yaml` directly and write down the
selection rule (skip near-black and near-white; index 0 → main, index 1 → secondary).

### G4: Logo images · blocks L3

`static/logos/miccai_YYYY.png` are five PNGs. `DESIGN.md` says plainly "the human provides
these files" and records that all five were verified transparent on 2026-07-13, but no
source URL is recorded for any of them and there is no download script.

**To close:** record the source URL per logo in `DESIGN.md`.

### G5: Host cities · blocks L3

`"city"` is hardcoded in `YEAR_META_RAW` (`build_site.py`), not in `config.yaml` where the
rest of the per-year settings live. It appears in the year-page header, the Explore-by-Year
cards and the logo `alt` text.

### G6: `has_white_bg` flag · blocks L3

Also hardcoded in `YEAR_META_RAW`. Currently `False` for all five years; the white-pill
wrapper it controls is dead markup kept for a future logo with a baked-in background.

**To close G5 + G6:** move `city` and `has_white_bg` into the per-year blocks of
`config.yaml` alongside `review_scale_max`.

### G7: Oral schedule PDFs · blocks L3

`data/manually_downloaded/OralSchedules/YYYY.pdf` are the source for every number
on the Orals & Spotlights page, and no code fetches them. MICCAI publishes the
program as a PDF program book per year, at a different URL each time and with
no stable pattern, so they were collected by hand.

This gap is narrower than it looks: the PDFs are small (868 KB for all five) and
committed, so anyone with the repo can re-run `extract_orals.py` and reproduce the
extraction bit-for-bit. What cannot be automated is *acquiring a new year's PDF*.

**To close G7:** record each year's program-book URL in `config.yaml →
oral_schedules` and add a fetch step. Worth doing only if MICCAI ever settles on a
predictable URL; until then, the manual step is one download per year.

**Not a gap:** `data/oral_title_overrides.yaml` is a hand-edited input, but it is
currently empty (all 377 presentations matched exactly), and `match_orals.py`
fails loudly rather than silently degrading if a future year needs entries.

## 6. Other issues found during the audit

These are not missing visualisations. They are things that will mislead someone trying to
reproduce this work.

### I1: `scraper/config.yaml` is dead, and CLAUDE.md says otherwise

`CLAUDE.md` states that `scrape.py` reads `scraper/config.yaml` and that the two configs
must be kept in sync. That is not what the code does:

```python
# scraper/scrape.py:38
CONFIG_PATH = Path(__file__).resolve().parent.parent / "config.yaml"
```

`parent.parent` is the repo root, so `scrape.py` reads the **root** `config.yaml`. Nothing
in the repository reads `scraper/config.yaml`. It is a stale duplicate that has already
drifted - it is missing `chart_settings`, and missing `coauthorship_network_min_papers`
and `num_top_papers` from all five year blocks. Someone editing it to change scraper
behaviour would see no effect and have no error message to explain why.

**Fix:** delete `scraper/config.yaml` and correct the CLAUDE.md repository-layout section.

### I2: Dependencies are unpinned in the two places that matter

`requirements.txt` lists 17 packages with **no version constraints at all**.
`.github/workflows/deploy.yml` installs with a bare `pip install plotly jinja2 networkx
numpy pandas pyyaml`. Only `uv.lock` pins anything, and CI does not use it.

Chart output is sensitive to the Plotly version, and every generated chart picks its CDN
script from `plotly.offline.get_plotlyjs_version()`, so a Plotly upgrade silently changes
what the published pages load. Today that is 3.7.0. A rebuild six months from now will
not necessarily produce the same site.

Updated 2026-09-01: an upgrade now also drops the Subresource Integrity attribute from
the partial bundles, because `_BUNDLE_SRI` in `build_charts.py` pins their hashes per
plotly.js version and plotly vendors only the full bundle. That is a warning in the build
log, not an error, and the site still works without it. See "Plotly bundle selection" in
CLAUDE.md for how to restore it.

**Fix:** pin versions in `requirements.txt` and have CI install from it.

### I3: The published site depends on three CDNs at view time

Generated pages fetch plotly.js from `cdn.plot.ly` (55 references as of 2026-09-01: 32
to `plotly-basic-3.7.0.min.js`, 18 to `plotly-3.7.0.min.js` and 5 to
`plotly-gl2d-3.7.0.min.js`), `cdn.jsdelivr.net/npm/d3@7` (5), and Inter from
`fonts.googleapis.com`. The site does not work offline and will degrade if any of the
three changes. This is a deliberate trade-off - it keeps the repository small, but it
belongs in the record.

### I4: Two chart functions are intentionally dormant

`chart_subject_bump` and `chart_subject_heatmap` are fully implemented and tested but not
called from `main()`; `main()` actively deletes their stale output. They were dropped in
the 2026-08 redesign for restating the same data as Trending Topics + Biggest Movers.
Re-enable by restoring the call in `main()` and the card in `templates/index.html`.
**This is a documented choice, not a gap.**

### I5: One documented feature has no code ~~(open)~~ RESOLVED 2026-08-31

`templates/index.html` used to carry a Jinja comment describing a parked
`chart_map_all_annotated` / `charts/map_all_annotated.html`: cluster names drawn
directly on the semantic map. The function never existed in `build_charts.py`, so the
template documented a feature the code did not have. It was parked because the UMAP
clusters are not tight enough for one label at each centroid to be honest; several
topics are spread out or sit far from their neighbours, and there is no colour legend
to read them against. The comment was removed on 2026-08-31 during a pass over the
page's wording, which closes the mismatch: nothing in the templates now describes a
chart that cannot be built.

### I7: `README.md` is one line ~~(open)~~ RESOLVED 2026-08-17

`README.md` now describes the project, its headline numbers, and the fastest path to a
working local build, and `CONTRIBUTING.md` walks through every pipeline stage and says

### I8: four review-parser bugs ~~(open)~~ RESOLVED 2026-08-22

The scraper was silently dropping review text. "Please provide detailed and
constructive comments for the authors" matched no branch of the field chain, so that
answer was discarded for every review in 2021 to 2024 (8,254 reviews). The
post-rebuttal justification label reads "justify your decision" in 2022 to 2024 but
"justify your final decision" in 2025, and only the latter was matched, losing 6,626
more. In 2024, two form questions both contained the word "reproducibility" and the
second overwrote the first in 1,352 reviews. And one 2024 page splits a review's
fields across two `<ul>` blocks, of which only the first was read.

Roughly **7.1 million characters**, about a third of the review text, were missing.
`text_detailed_comments` feeds Avg Review Length on the overview page, so that panel
showed reviews growing 78% from 2021 to 2025 when the real rise is about 15%.

Fixed, and 2021 to 2024 re-scraped; paper counts, ids, titles, and review counts are
unchanged, and all 377 oral talks still match by exact title.

**The lesson matters more than the bugs.** Every check in this repository, and every
check run while hunting these, went through `miccai_all.json`. That can never find
this: a field the parser never captured leaves no trace in the data, so the data looks
complete and self-consistent. `scraper/audit_review_fields.py` now compares live pages
against what the parser extracts, and should be run whenever a year is added.

### I9: the co-authorship charts are not reproducible ~~(open)~~ RESOLVED 2026-08-30

The five `coauthor_YYYY.html` files come out different on **every build, from identical
data and identical code**. Node positions, node ordering, and the community colours all
move. The other 55 chart files are byte-identical between builds once Plotly's
per-build `<div>` ids are normalized (that normalization is itself no longer needed;
see the resolution below).

This was verified directly: two consecutive `build_charts.py --years 2021` runs on an
unchanged working tree produced different output; the same two runs with
`PYTHONHASHSEED=0` produced identical output.

**Cause:** Python randomizes `hash(str)` per process unless `PYTHONHASHSEED` is set, so
any set of author names iterates in a different order each run. `_coauthor_data` builds
the graph from such a set, which changes the node order handed to `spring_layout` and
to `greedy_modularity_communities`. The `seed=42` already on `spring_layout`
(`build_charts.py:1119`) cannot help, because the *input order* is what varies.

**This falsifies the L1 claim above for these five files.** "Fresh clone → identical
website" holds for everything else.

It is cosmetic rather than wrong: the graph, the communities, and the counts are the
same each time, only their arrangement on screen differs. But it means a rebuild always
shows a diff, which hides real changes among noise.

**Fixed on 2026-08-30**, in three places rather than the two predicted above. The
first two were as expected: `_coauthor_graph` now sorts the active-author set before
inserting nodes, and both `sorted()` calls on components and communities now break ties
on the first member instead of leaving equal-sized groups in set order.

The third was not obvious and is worth recording. With those two fixed, the node order,
the communities, and the components were all stable, and the layout still moved. The
cause is `G.subgraph(comp)`: it returns a filtered **view**, and networkx iterates
whichever container is smaller, so when a component is less than half the graph it walks
its own internal `set` of permitted nodes rather than the graph's ordered dict. The
view's node order is therefore set order even when the graph's is not, and
`spring_layout` seeds initial positions by node index. `_coauthor_layout` now builds
each component as an explicit `nx.Graph` with `sorted(comp)` nodes. Note that
`G.subgraph(sorted(comp))` would NOT have worked: networkx converts the argument to a
set regardless.

**Verified:** three full `build_charts.py` runs under `PYTHONHASHSEED` 1, 2, and 12345
produce **all 61 chart files byte-identical**, and `build_site.py` likewise produces
identical pages and `papers.json`. Setting `PYTHONHASHSEED` in the deploy workflow was
rejected as a fix: it would mask the problem in CI and leave local builds drifting.

Fixed alongside it: `pio.to_html` stamped a fresh random UUID as the `<div>` id of every
chart on every build, which is why the "once ids are normalized" caveat appears above.
`save_chart` now passes an explicit `div_id` derived from the filename, so no
normalization is needed to compare two builds. **L1 now holds for the whole site**, with
the single documented exception that the footer carries the build date.

Not fixed here because it is unrelated to the work that found it, and fixing it means
editing `build_charts.py`, which that work was explicitly scoped away from.
